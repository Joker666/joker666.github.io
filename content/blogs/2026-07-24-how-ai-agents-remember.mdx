I have been thinking about what people mean when they say an AI agent has memory. The word gets used for almost everything. The conversation history is memory. A vector database is memory. A `MEMORY.md` file is memory. Even a large context window is sometimes sold as memory.

But the model does not remember a previous API call. We send it a collection of messages, tool results, and instructions, it produces an output, and that call is over. On the next call, the agent has to assemble everything again.

So where does memory come from?

> An agent remembers by rebuilding the right context for its next action.

Deciding what "right" means is the whole problem. Include too little and the agent repeats work it has already done. Include too much and useful information gets buried under old file contents, command outputs, and conversations. From what I can tell, agents currently handle this in three broad ways: compact the current context, retrieve old information from external storage, and turn past work into reusable experience.

### The Context Window

Before getting into the three approaches, it helps to separate the model from the agent. The model has a context window. The agent is the system around it that fills that window.

A coding agent's context might look something like this:

```text
system instructions
repository instructions
conversation
files it has read
tool calls and their results
current plan
```

All of this is sent to the model as input. If the agent reads a 2,000-line log file, those lines now compete with the original task for attention. A one-million-token context window gives us more room, but it does not decide which 2,000 lines matter. It only postpones that decision.

Prompt caching is useful here, but I don't think it is memory. Caching can make a repeated prefix cheaper to process. It does not choose what the agent should remember.

### Approach 1: Context Compaction

The simplest way to keep an agent running is to shrink its history when it gets too large. This is usually called compaction or context editing.

Some content can be removed without much thought. If an agent reads a file, changes it, and reads the new version, the first copy is probably useless. The same goes for a test failure that has already been fixed. Tool results take up a surprising amount of the context, so deleting stale results can buy a lot of room.

Eventually deletion is not enough. The agent has to summarize:

```text
Before:
    40 messages
    12 file reads
    8 test runs
    3 failed attempts

After:
    We changed the authentication middleware.
    The remaining failure is in the refresh token test.
    Do not change the public API.
```

The summary becomes a smaller representation of the work so far. It is similar to compressing a log into a checkpoint and continuing from there.

This works well for the current task, but it is lossy. The summary may record that an approach failed and leave out the exact error that explained why. It can preserve the final decision but forget a constraint that led to it. Once the original context is removed, the agent cannot recover what the summary missed.

There is also a strange feedback loop here. We ask the same model that filled the context to decide which parts of that context future calls will need. Most of the time this is fine. Sometimes the model confidently throws away the one detail it should have kept.

### Approach 2: External Memory and Retrieval

Compaction helps an agent survive one long task. It does not help much when I start a new session tomorrow. For that, the agent needs storage outside the context window.

The common solution is to save conversations, facts, task results, or files and retrieve a small set before each model call. The first version usually looks like this:

```text
memory -> embedding -> vector database

new task -> embedding -> similarity search -> relevant memories
```

If the new task is about deploying a Go service, semantic search might retrieve notes from previous Go deployments. This is already much better than injecting the entire history.

It also breaks in some annoying ways. Semantic similarity is not the same as usefulness. An old deployment error may look very similar to the current one but belong to a different repository. Exact names and error codes sometimes work better with keyword search. Recency matters. Permissions matter. And facts change.

Imagine the memory store contains both of these:

```text
Rafi prefers Python for backend services.
Rafi now prefers Go for backend services.
```

A vector search can easily retrieve the first one. Both are relevant and semantically similar, but only one is current. Now we need timestamps, metadata, ranking, invalidation, and rules for resolving conflicts. We started with embeddings and somehow ended up rebuilding a database.

Newer memory systems mix vector search with keyword search and metadata filters to handle these cases. Some use temporal knowledge graphs so that relationships can change without erasing their history. The graph can represent that one fact replaced another, instead of treating both as equally valid chunks of text.

I think this is where "agent memory" becomes a slightly misleading term. Much of the difficult work is familiar information retrieval and database engineering. What should we write? How should we index it? How long should we retain it? Which result is authoritative? The LLM makes those decisions fuzzier, but it does not make them go away.

### Approach 3: Learning From Experience

Saving and retrieving old events is useful, but an agent that remembers every event has not necessarily learned anything from them.

Suppose an agent spends 30 minutes trying to build a repository. It runs the build six times, searches through configuration files, and eventually discovers that generated database types must exist before TypeScript can compile. We could store the whole trajectory and hope a search finds it later. Or we could save one procedure:

```text
Before building this repository, run `pnpm db:generate`.
```

The second version keeps the useful lesson and drops the transcript that produced it.

Memory systems often borrow three categories from cognitive science:

- **Semantic memory** stores facts, such as a user's preferences or a project's architecture.
- **Episodic memory** stores previous experiences, including what the agent tried and what happened.
- **Procedural memory** stores how to do something, such as a runbook or an instruction.

The categories are useful, although real memories do not always fit cleanly into one box. A debugging session can contain facts about the codebase, an episode about a failed fix, and a new procedure for running the tests.

Agents can form these memories while they work or in a separate reflection step. After a task, another model call examines the trajectory and asks what is worth keeping. Over time, several similar episodes can be consolidated into one general rule. A coding agent might stop remembering five individual migration failures and keep a single runbook for database changes.

This is the newest of the three approaches, and I find it the most interesting. It is also easy to get wrong. A lesson learned from one failure may not apply to the next project. The agent can extract the wrong lesson, store it with complete confidence, and make every future run worse. Forgetting and correcting memories are as important as creating them.

Recent work goes one step further and treats memory management as a policy. Instead of always saving a summary or always retrieving the nearest five chunks, the agent learns when to write, retrieve, update, and forget. Memory management then becomes another decision the agent has to make while it works.

### Putting Them Together

These approaches solve different parts of the same problem.

```text
                       new task
                          |
                          v
             retrieve relevant old memory
                          |
                          v
                build the working context
                          |
                          v
                    agent works
                          |
              +-----------+-----------+
              |                       |
              v                       v
       compact current work     extract useful lessons
              |                       |
              +-----------+-----------+
                          |
                          v
                  external memory
```

Compaction keeps the current task within the context limit. Retrieval brings information back across tasks and sessions. Consolidation tries to turn the history into something more useful than a pile of transcripts.

A practical agent will probably use all three. It keeps recent messages in the prompt, clears stale tool results, writes durable notes to files or a database, and occasionally turns repeated experience into an instruction. The exact implementation can be a sophisticated temporal graph or a folder full of Markdown files. The hard questions stay the same.

What deserves to be remembered? When is an old memory no longer true? How does the agent know that a retrieved memory is relevant rather than merely similar? I don't think we have great answers yet.

At first, I thought a larger context window would eventually make agent memory less important. Now I am not so sure. A larger desk is useful, but at some point someone still has to clean it.
